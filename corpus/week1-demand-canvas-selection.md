# W1：需求画布 + 技术选型（Lu 2026-10-30 校正版）

对应 6 周完整版第 1 周。验收标准：能用 10 分钟讲清“为什么是这个场景、为什么是这套栈”。

说明：初稿按 JD 四条职责 + Lu 已有经验推导，2026-10-30 经 Lu 校正（用户演变、ROI 估算数字、KListView 例子、痛点排序、LangGraph 澄清，及同日两条补充：定界耗时修正为 1–2 小时、W3 工具集扩展到日志）。ROI 数字是 Lu 凭感觉估算、非统计，讲的时候要先声明。M1 模板引擎不能写成 Agent 经验，面试要主动区分。

## 一、研发测试全链路

需求 → 测试设计 → 用例执行 → 缺陷流转 → 回归 → 发布质量门

Agent 只切其中一段：缺陷流转里的“定界” + 回归里的“用例生成／筛选”。不碰全链路，不另起聊天机器人。

## 二、AI 最值得切的 3 个痛点（Lu 2026-10-30 校正后排序）

1. **历史用例没沉淀或缺少维护**（最痛）：用例资产没有沉淀下来、缺少维护，改动来了找不到对应的用例，新人重复踩坑，相似问题重复劳动。这是回归范围只能靠拍脑袋的根因之一。
2. **回归范围靠拍脑袋**（最痛）：改动一处，不知道该跑哪些用例。跑全量贵、跑少了漏网，范围凭感觉，没有“改动—用例”关联依据。
3. **缺陷定界依赖个人经验**：缺陷报告来了，人工读堆栈、定位代码、凭经验猜模块和可疑点。新人慢、老人忙，定界质量因人而异。

排序变化的影响：W2 分层知识库的 L1 结构化知识要把“用例—模块—改动”映射做实，否则回归范围还是拍脑袋；知识库不只是存历史缺陷，更要解决用例的沉淀与维护。

## 三、不值得做的 2 个点

1. **通用问答／聊天机器人**：不解决测试团队的具体痛点，ROI 没法衡量，也对不上 JD 的研发测试场景。
2. **训大模型／追所有新框架**：试点阶段成本高，且与岗位要求的“解决方案设计与交付”不匹配。用现成模型 + 工程化分工即可。

## 四、场景画布（1 页）

- **用户是谁**：前期是专职测试；后来公司推研发也要兼顾部分测试。所以交付版要同时给两类人用：测试同学和兼做测试的研发（后者能接受更多技术细节，但同样需要“不用看代码也能跑通”的入口）。
- **现在手工怎么做**：收到缺陷报告／Crash 堆栈／PR diff → 人工读堆栈、定位代码 → 翻历史相似缺陷（靠记忆和搜索）→ 凭经验定模块和可疑点 → 手工挑回归用例、写验证步骤。
- **耗时和出错点**：人工定界一个缺陷凭感觉约 1–2 小时（Lu 同日修正：简单缺陷会摊薄平均耗时，原先 4 小时高估；无具体统计）。全 App 回归要 10 多个域的测试参与 1–2 天，业务域回归约 QA 2 人日（同为估算）。这几个数是 ROI 的分母，口径是“凭感觉估算”，不是统计值，讲的时候要先声明。出错点：定界慢且因人而异；相似缺陷重复定界；回归范围凭感觉，多跑浪费、少跑漏网。
- **AI 做完省什么**：定界给模块 + 可疑代码 + 证据引用（不是一句话结论）；回归用例自动生成并过可执行性检查；人工只做复核，不做从头排查。
- **失败了谁兜底**：人工复核环是兜底。检索为空、定位冲突、用例不可执行时各自降级；没有证据的定界标“未知”，不编模块名。

## 四附、亲历例子一：KListView 自动算高后 contentOffset 跳变（Lu 提供，脱敏后可用）

- 现象：KListView 实现自动算高后，部分 iOS 13 小版本上列表 contentOffset 出现跳变。
- 排查过程：各阶段打大量日志（特别是 UICollectionView 生命周期、算高函数、延迟打印实际宽高）未排查出问题；后面通过回退 commit 逐步缩小范围才定位，耗时 1 天。
- 对 Agent 的启示：这不是 Crash 堆栈类缺陷，是版本相关的 UI 行为 bug。定界需要的不是“读堆栈猜模块”，而是：按时间／版本收窄范围、结合 commit 历史做二分缩小、把“日志没查出问题”本身当成证据（排除法）。W3 的工具设计要包含查代码、查 commit 历史、查系统日志、查业务日志，不能只查知识库。
- 注意：缺陷类型不限于 Crash，场景画布的输入保持“缺陷报告／堆栈／PR diff”三类。

## 四附、亲历例子二：个人项目 AlarmKit 强提醒 App（Lu 提供，Claude Code 工作流证据）

- 起因：iPhone 日程中添加的提醒 push 太弱，导致生日、纪念日易错过；Lu 开发了一个利用 iOS 26 AlarmKit 强系统闹钟提醒的 App。
- 关键做法：利用 Claude Code 查系统日志＋App 日志，逆向 Alarmy“关闹钟直接拉起 App”的核心能力；排查 bug 也大量用 Claude Code 查系统＋App 日志的能力。
- 对 Agent 的启示有两点。第一，W3 工具集必须包含日志类工具：查系统日志、查业务日志，与查知识库、查代码、查 commit 历史并列，缺了日志就复现不了这类行为 bug。第二，回归执行环可以直接复用 Lu 的 Claude Code 工作流：修完 bug 后自动构建、自动安装、自动跑单元测试和 UI 测试做回归；剩余少部分（例如需要生物识别的、模拟器无法操作的）交由人工复验——这正是工作流里“自检 → 人工复核”环节的落地形态，W3 自检设计和 W4 验收都可以按这个闭环写。

## 五、选型表（含放弃的理由）

| 层 | 选型 | 理由 | 放弃的 |
|---|---|---|---|
| 可控工作流 | LangGraph 状态机：解析缺陷 → 检索知识 → 定界假设 → 生成用例 → 自检 → 人工复核（LangGraph 不放弃，它就是核心选型） | 步骤、工具调用、失败降级都显式可控，符合“设计并实现高效的智能体任务处理逻辑”；LangGraph 本就属于 LangChain 生态，LangChain 的模型封装、工具等组件按需用，不单独成框架 | 纯 prompt 链／单次调用：不可控，失败难降级 |
| 交付版 | Dify 复刻同一流程 | 测试同学能改 prompt、换知识库，证明“交付给非研发用户”这一层 | 只给研发用的 API 单一形态：JD 第 2 条要的是交付到测试团队 |
| 向量库 | pgvector | Postgres 生态、Docker Compose 一键起、试点成本低 | 自建向量服务／重型 Milvus 集群：试点阶段过重 |
| 模型分工 | 大模型做定界推理＋小模型做分类和去重＋prompt／结果缓存 | 成本和延迟可算账，W5 能讲清取舍 | 一个大模型包办一切（成本、延迟失控）；训专属模型（试点 ROI 低） |
| 服务化 | FastAPI＋Docker Compose（API、pgvector、Redis 队列） | 本地可复现，W4 验收“别人不用看代码也能跑通” | 一开始就上 K8s 集群实操：W5 只到部署清单＋监控 |
| 语言 | Python | FastAPI／LangGraph 生态 | Java 重学：定位为“能对接现有 Java 测试平台 API”即可 |

## 六、W1 验收：10 分钟讲稿提纲

- 3 分钟场景：用户是谁、手工怎么做、3 个痛点、2 个不做点。
- 3 分钟方案：状态机六步、工具分离（查代码／查知识库／查 commit 历史／查系统日志／查业务日志）、防幻觉（证据引用，无证据标未知）。
- 2 分钟栈与选型理由：LangGraph＋Dify 同一场景两种交付形态、pgvector、大小模型分工。
- 2 分钟验收与风险：W3 跑通 5 个真实缺陷样本、人工接受率可统计；风险是幻觉、数据脱敏、成本失控，各有兜底。

## 七、校正结果（Lu 2026-10-30 已答，含同日补充）

1. 用户角色：前期专职测试，后来研发兼顾部分测试——已写入第四节。
2. ROI 分母数字：人工定界凭感觉约 1–2 小时（同日修正：简单缺陷摊薄平均耗时，原 4 小时高估）；全 App 回归 10 多个域 1–2 天，业务域回归 QA 约 2 人日——均为估算非统计，已写入第四节。
